# Plan: a cost-efficiency re-analysis of TRIZ priming

Status: v1 and Phase 2 both complete (see repo root `README.md`). The hypotheses below were
written down, and the threshold + test design fixed, **before** `score_solutions.py` was
run — in the style of `IM-LLM`'s persona follow-up (`persona_as_factor/README.md`) and
`triz-on-vs-off-agent`'s own `M6_50ideas/README.md`. The "Result" line under each hypothesis
was added after Phase 2 ran; nothing above it was edited afterward.

## Background

`triz-on-vs-off-agent` (`run: factorial_129`) already ran a 2x2 factorial: prompt length
(long / short) x TRIZ priming (on / off), 4 generator models, 40 problems with usable
TRIZ-on/off pairs, judged blind 2AFC in both presentation orders by a cross-family jury,
plus — new this session — the decision-model judge Jev.

v1 of this repo took that existing data and asked a cost question instead of a quality
question: TRIZ-on costs +46 to +85 tokens per call over TRIZ-off at matched prompt length,
and buys no win-rate advantage that clears a case-clustered 95% CI (see root `README.md`,
"Results"). That's a real finding, but it's built on a *coarser* signal than IM-LLM's: a
binary pairwise pick, not an absolute per-solution score. IM-LLM's actual headline measure —
yield, top outputs per 100k tokens — needs the finer signal. Phase 2 gets it.

## Why the finer signal wasn't already available

The factorial evaluator prompt (`prompts/factorial/E_TRIZ_OFF.txt` in the sibling repo) asks
the judge for an explicit `SCORE A: 0-10` / `SCORE B: 0-10` before its final `ANSWER:` line.
That score was asked for and generated by every judge call that has ever run — it was just
never kept: `judge.py`'s cache record stores `"raw": (content or "")[:400]`, and the scores
sit at the *end* of the judge's response, after a paragraph or more of reasoning, so they
were truncated away before ever reaching disk. The fix isn't a new prompt; it's storing what
was already being asked for.

## RQ2 (Phase 2)

> Does TRIZ priming produce a higher top-solution rate per 100k tokens than TRIZ-off, at
> matched prompt length — mirroring IM-LLM's finding that more context does not raise yield
> even when it raises mean quality?

## Hypotheses, written down before Phase 2 runs

- **H1 (TRIZ costs more per top solution).** TRIZ-on's yield (top solutions / 100k tokens,
  matched prompt length) is *lower* than TRIZ-off's. Supported if the 95% CI of the yield
  ratio (TRIZ-on ÷ TRIZ-off) is below 1. This is the predicted direction, based on v1: a real
  token premium with no detected win-rate edge should show up as lower yield once yield can
  be computed directly.

  **Result (both prompt lengths, threshold 2.2 of 0-4, ~12% of all solutions):** not
  confirmed at the case level. Long prompt: yield is flat (TRIZ-on 11.05 vs TRIZ-off 10.81
  per 100k tokens; pooled P(on higher)=0.95, per-case sign test 10-8 of 40, p=0.81). Short
  prompt: the pooled, token-weighted estimate favours TRIZ-off clearly (13.38 vs 18.52,
  pooled P(on higher)=0.000), but the per-case sign test does **not** confirm it (TRIZ-on
  wins only 6 of 40 cases, p=0.33) — a pooled-only signal, likely driven by a few
  token-light, hit-heavy TRIZ-off cases, not a case-general effect. A stricter 2.3 threshold
  (~10% kept) shows the same split (pooled favours TRIZ-off at both lengths, p≈0.000-0.002;
  neither case-level sign test clears p<0.05). See root `README.md`, "Results (Phase 2)",
  and `results/yield.csv` / `results/yield_strict.csv`.
- **H2 (length is the bigger yield cost).** The long-prompt pair's yield gap from the
  short-prompt pair (at the same TRIZ setting) is larger than the TRIZ-on/off yield gap at
  matched length. Supported if |long−short yield ratio − 1| > |TRIZ-on/off yield ratio − 1|
  at both prompt lengths. Based on v1's +665/+704-token length cost against a
  worse-than-coin-flip win rate.

  **Result:** not yet tested directly (the comparison needs `P_L_TRIZ_ON vs P_S_TRIZ_ON` and
  `P_L_TRIZ_OFF vs P_S_TRIZ_OFF` run through `yield_analysis.py`'s same machinery, which
  currently only wires up the two matched-length TRIZ-on/off pairs — `MATCHED_PAIRS` in
  `scripts/yield_analysis.py` would need the other two pairs added). Flagged as the next
  small addition, not done in this pass.
- **H3 (null).** Neither H1 nor H2 holds — TRIZ-on's extra reasoning tokens translate into
  enough extra top solutions that yield is flat or higher.

  **Result:** this is closer to what happened at the case level — H1 is not confirmed by the
  per-case test at either prompt length, so the honest summary across both v1 and Phase 2 is
  a **null on win rate and a null on yield**, not a confirmed cost penalty. The one place a
  real signal appears (short-prompt pooled yield) doesn't survive the stricter, case-general
  test, which is exactly the check it was built to apply.

## Design

1. **Scoring call.** For every solution that has ever been generated in `factorial_129`
   (one call = one solution; ~320 unique solutions across the 4 arms x 40 cases x up to 4
   models), ask Jev (cheap, already integrated — see sibling repo's `src/judge.py --jev`) a
   single `score` question per solution: *rate this solution's creativity 0-10 against the
   same five-part rubric already in use* (originality, usefulness, feasibility, specificity,
   elegance — the sibling repo's `prompts/factorial/E_TRIZ_OFF.txt` rubric). Scored
   independently of any pairing, so it's not reusing or re-deriving the truncated pairwise
   judgements.
2. **Threshold.** Follow IM-LLM §3.6 exactly: report the share of all solutions each
   candidate threshold keeps (no exact top-10% exists on a coarse scale), pick the nearest
   step to 10%, and report a stricter cut as a robustness check.
3. **Yield.** `top solutions / 100k tokens`, per arm, token counts from this repo's existing
   `data/calls.csv` (already computed, zero marginal cost to reuse).
4. **Uncertainty.** Case-clustered bootstrap (2,000 resamples, calls resampled within case),
   matching `tail_charts.py`'s `bootstrap_yield` and this repo's own `cost_efficiency.py`.
5. **Arm comparison.** Exact two-sided sign test across cases, as in both parent repos.

## What would change the plan

If H3 (the null) holds, the honest framing flips from "TRIZ costs more per good idea" to
"TRIZ's token cost and its (currently undetected) quality edge roughly cancel" — worth
reporting either way, since v1 already shows the cost side is real regardless of which way
Phase 2 lands.
